# Соглашения о коде

Правила, которые проверяются автоматически, и правила, которые держатся на ревью. Цель одна:
файл или класс не должны превращаться в свалку, а уже выросшие — уменьшаться по мере правок,
а не переписываться за один раз.

## Размер файла

| Что | Лимит |
|---|---|
| Любой файл исходников и тестов (`src/`, `tests/`) | **1000 строк** |
| Новая единица кода (класс, модуль) | один файл `.cpp` + один `.h` |

Лимит действует и на новые файлы: файл длиннее 1000 строк не появится, даже если он новый —
CI его не пропустит. Проверяет `tools/Size-Ratchet.ps1` на каждом pull request. Файл длиннее
лимита считается техническим долгом и попадает в базовую линию `tools/size-baseline.json`.

## Храповик размера файлов

Долг не растёт и не гасится разом — он **только уменьшается**, шаг за шагом, когда файл и так
правится.

```powershell
./tools/Size-Ratchet.ps1            # проверить (это же делает CI)
./tools/Size-Ratchet.ps1 -Report    # 25 самых больших файлов и их потолки
./tools/Size-Ratchet.ps1 -Write     # затянуть храповик после того, как вынесли часть
```

Как это работает:

- файл **не больше** лимита — свободен, в базовой линии его быть не должно;
- файл **больше** лимита — записан с потолком, равным текущему размеру;
- файл вырос выше потолка — CI **падает**: сначала вынесите часть, потом добавляйте;
- файл уменьшился — CI **падает** с просьбой выполнить `-Write`: потолок опускается до нового
  размера, и вернуть прежний уже нельзя;
- новый файл длиннее лимита — CI **падает**: его нужно разделить.

Поднять потолок скрипт не умеет. Единственный способ — править `tools/size-baseline.json` вручную
в отдельном PR, и тогда рост долга виден в диффе. Это осознанное действие, а не побочный эффект.

Практическое следствие: если файл дошёл ровно до лимита, следующая строка добавляется только
вместе с выносом — либо вы удаляете что-то ещё в этом же файле, либо разделяете файл.

### Как уменьшать большой файл

Не переписывать целиком. За одну правку — одна связная часть:

1. Выберите группу функций или методов с общей ответственностью (диалог, парсинг, отрисовка
   списка), а не «первые 300 строк».
2. Вынесите её в новый `x.h` + `x.cpp`; заголовок — только объявления, реализация — в `.cpp`.
3. Тесты этой части перенесите рядом с ней (или в отдельный файл тестов).
4. Сборка и тесты — зелёные, затем `./tools/Size-Ratchet.ps1 -Write`.
5. Повторяйте при следующих правках файла. Файл на 2 500 строк — это 6–8 таких шагов, не один.

## Класс и функция

Проверяется на ревью; счётчики — ориентир, а не догма:

- **класс** — одна причина для изменения; больше ~10 публичных методов или ~15 полей — повод
  разделить по ответственности;
- **функция** — до ~50 строк и один уровень абстракции; если внутри уже есть `switch` по режимам
  окна, это кандидат на отдельную функцию;
- **заголовок** — объявления и короткие встраиваемые методы; логика — в `.cpp`;
- **`main.cpp` утилиты** — разбор аргументов, вызов и печать результата. Логика — в `core/`.

Существующие большие классы не трогаем ради самого разделения: выделяем часть, когда правим
файл по другой причине. Так же, как с храповиком.

## Размещение

- общая логика — `src/core/`, утилиты — `src/tools/<имя>/main.cpp`, перехваты — `src/hook/`.
- новый компонент `core/` — пара `.cpp`/`.h` и строка в `src/core/CMakeLists.txt`;
  заголовок подключается как `"Config.h"`, без путей.
- тест к новому компоненту — отдельный файл в `tests/`, регистрация — в `tests/main.cpp`.

## Стиль

Действующий код — образец: отступ в 4 пробела, `#pragma once`, пространство имён `approute`
в `core/`, комментарии по-русски, сообщения пользователю по-русски.
