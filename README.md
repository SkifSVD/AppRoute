# AppRoute

Маршрутизация по приложениям для Windows: выберите программу и укажите, через какой сетевой
интерфейс (Wi-Fi, Ethernet, VPN-туннель) она ходит в сеть. Весь остальной трафик идёт через
основное подключение — независимо от того, в каком порядке подключались VPN-клиенты.

*Per-application network interface routing for Windows 10/11.*

> **Статус:** ранний прототип. Готовы консольный менеджер маршрутов, привязка TCP/UDP и DNS
> приложений через hook-DLL (x64 и x86), конфиг правил и окно правил `approute-gui`; остальной
> GUI — в работе ([план](https://github.com/SkifSVD/AppRoute/milestones)).

## Проблема

Каждый VPN-клиент (OpenVPN, Xray/Happ в TUN-режиме, WireGuard…) при подключении забирает
маршрут по умолчанию себе: ставит `0.0.0.0/0` с минимальной метрикой или пару
`0.0.0.0/1` + `128.0.0.0/1`. В итоге «главным» становится тот, кто подключился последним, а
приложения при переподключении уезжают в текущий туннель.

## Как AppRoute это решает

1. **Менеджер маршрутов** держит маршрут по умолчанию на основном интерфейсе:
   - поднимает метрику интерфейсов VPN (от неё зависит и порядок DNS-серверов);
   - заменяет расщеплённые `0/1` + `128/1` (в IPv6 — `2000::/3`, `2000::/4` + `3000::/4`) на `0/0`,
     который проигрывает основному;
   - добавляет `0/0` с низким приоритетом на интерфейсы без него, чтобы к ним можно было
     привязывать приложения;
   - следит за изменениями (переподключение VPN) и всё откатывает при выходе.
2. **Привязка приложений** *(в разработке)* — DLL внедряется в выбранный процесс и привязывает
   его сокеты (TCP и UDP) к IP выбранного интерфейса; DNS-запросы приложения идут через DNS этого
   интерфейса. Windows (strong host model) отправляет такие пакеты только маршрутами этого
   интерфейса.
3. **WFP-драйвер** *(в планах)* — тот же результат на уровне ядра, без внедрения DLL.

## Сборка

Нужны Visual Studio 2022+ с компонентом «Разработка классических приложений на C++» и CMake
(входит в VS). Зависимость [MinHook](https://github.com/TsudaKageyu/minhook) подключена
git-подмодулем.

```powershell
git clone --recurse-submodules https://github.com/SkifSVD/AppRoute.git
./build.ps1            # Release → build/bin/Release
./build.ps1 -Config Debug
./build.ps1 -Test      # сборка и модульные тесты (ctest)
```

## CI

Сборка выполняется на self-hosted runner с метками `self-hosted, Windows, X64, approute`
(нужны Visual Studio с C++ и PowerShell 7). Пока runner не запущен, задания ждут в очереди.

## approute-gui (окно правил)

```powershell
approute-gui                      # правила из %APPDATA%\AppRoute\config.json
approute-gui --config FILE        # другой файл правил
approute-gui --run PROGRAM [-- ARGS]   # запустить программу по правилу без окна (так работают ярлыки)
```

Список правил «программа → интерфейс» с текущим состоянием интерфейса (подключён, отключён,
нет в системе) — оно обновляется само каждые 3 секунды, например при подключении VPN.

- **Добавить** — мастер из трёх шагов:
  1. программа — из установленных в Windows (ярлыки меню «Пуск» и зарегистрированные программы,
     с поиском), а если её там нет — файл программы или ярлык (`.lnk`), который указывает на неё;
  2. интерфейс — из подключённых сейчас или из истории (ранее выбранные, например отключённый VPN);
  3. что делать, если интерфейс недоступен: блокировать или пустить обычным маршрутом.

  DNS, IPv6 и дочерние процессы получают значения по умолчанию. Правило для той же программы
  дважды не создаётся. Приложения Microsoft Store в список не входят — их нельзя запустить
  через AppRoute.
- **Изменить** — все настройки правила: программа (полный путь, ярлык, или только имя файла —
  тогда правило действует в любом каталоге), интерфейс, недоступность интерфейса, DNS, IPv6,
  дочерние процессы.
- **Удалить** — с подтверждением (или клавиша Delete).
- **Запустить** — программа стартует с правилом, как через `approute-run`.
- **Ярлык…** — ярлык на рабочем столе или в меню «Пуск» (папка AppRoute) со значком программы:
  он запускает её через AppRoute (`approute-gui --run`), без окна и консоли. Если правило потом
  удалить, ярлык спросит, запустить ли программу без AppRoute. Для правила с одним именем файла
  ярлык не создаётся — нужен полный путь.
- **Обновить** — перечитать файл правил (его могли изменить `approute-config` или другой экземпляр).

Правила хранятся в том же `config.json`, что у `approute-config` и `approute-run`. Если файл
не читается, окно сообщит об ошибке и отключит правку, чтобы не перезаписать ваши данные.
Окно работает с правами пользователя и поддерживает разные масштабы мониторов (Per-Monitor DPI).

## approute-run (запуск программы через интерфейс)

```powershell
approute-run --adapter happ-xray -- "C:\Program Files\App\app.exe" --some-arg
approute-run --adapter "Беспроводная сеть" --log C:\temp\approute.log -- curl.exe https://ifconfig.me/ip
approute-run -- "C:\Program Files\App\app.exe"     # интерфейс — из правила в конфиге
```

Без `--adapter` правило для программы берётся из конфига (см. `approute-config` ниже);
`--config FILE` — другой файл конфига.

Программа запускается с `approute-hook64.dll`, которая перед каждым соединением привязывает
сокет к IP выбранного интерфейса (`connect`, `WSAConnect`, `ConnectEx`, `sendto`, `WSASendTo`,
`WSASendMsg`, `bind` на «любой адрес»). Локальная сеть, loopback и подсети других интерфейсов
не перенаправляются. Если у интерфейса нет адреса нужного семейства, соединение блокируется
или идёт маршрутом по умолчанию — по политике правила (см. «Если интерфейс правила недоступен»).
Права администратора не нужны, но у интерфейса должен быть маршрут `0/0` (см. `--ensure-default`
ниже). Поддерживаются 64- и 32-битные программы: для процесса другой разрядности (32-битная
программа, или 64-битный ребёнок 32-битного родителя) DLL внедряет помощник
`approute-inject32.exe` / `approute-inject64.exe`, поэтому все файлы из `bin` должны лежать вместе.

Правило распространяется на дочерние процессы (браузеры работают с сетью в отдельном процессе):
DLL перехватывает `CreateProcessInternalW`, запускает ребёнка приостановленным, внедряется в него
и восстанавливает правило в окружении, если родитель передал своё. `--no-children` — отключить.

DNS приложения тоже идёт через выбранный интерфейс: DLL перехватывает `getaddrinfo`,
`GetAddrInfoW` и `GetAddrInfoExW` и разрешает имена через DNS-серверы интерфейса, а если они
недоступны (VPN-клиент часто блокирует порт 53 в обход туннеля) — через DNS-over-HTTPS по тому
же интерфейсу. Так DNS не утекает в системный резолвер, который ходит через основной канал.
Подходят серверы в подсети интерфейса или с лучшим маршрутом через него. Имена из таблицы NRPT
(так корпоративные VPN, например OpenVPN, задают DNS внутренних доменов) разрешаются только у
серверов правила NRPT, если они достижимы через интерфейс, — внутренние имена не уходят во
внешний DoH.
`APPROUTE_DNS=system` отключает перехват. Требуется Windows 11 (используется `DnsQueryEx` с
пользовательскими серверами).

## approute-config (правила)

Правила хранятся в `%APPDATA%\AppRoute\config.json`:

```json
{
  "version": 1,
  "primary": "auto",
  "rules": [
    { "app": "C:\\Program Files\\App\\app.exe",
      "target": { "type": "adapter", "id": "{GUID интерфейса}" },
      "onUnavailable": "block", "dns": "adapter", "ipv6": "follow", "includeChildren": true }
  ]
}
```

```powershell
approute-config add "C:\Program Files\App\app.exe" --adapter happ-xray
approute-config add telegram.exe --adapter happ-xray --no-children   # по имени файла, в любом каталоге
approute-config show
approute-config remove telegram.exe
approute-config check
```

| Поле | Значения |
|---|---|
| `app` | полный путь (можно с `%ПЕРЕМЕННЫМИ%`) или только имя файла; полный путь важнее имени |
| `target.id` | GUID интерфейса — не меняется при переименовании; `add` переводит имя/ifIndex в GUID |
| `onUnavailable` | `block` (по умолчанию) / `default` — если интерфейс отключён, см. ниже |
| `dns` | `adapter` (по умолчанию) / `system` |
| `ipv6` | `follow` (как `onUnavailable`) / `block` / `default` — если у интерфейса нет IPv6 |
| `includeChildren` | `true` (по умолчанию) / `false` |

`knownAdapters` — история выбранных интерфейсов (GUID, имя, описание): по ней окно и
`approute-config show` показывают имя интерфейса, которого сейчас нет в системе (VPN отключён),
и предлагают его при добавлении правила. Заполняется само.

Неизвестные поля игнорируются; конфиг более новой версии не загружается, а не портится.

**Если интерфейс правила недоступен** (VPN отключён, у интерфейса нет адреса нужного семейства):

- `block` — соединения завершаются ошибкой `WSAENETUNREACH`, DNS-запросы — `WSATRY_AGAIN`;
  трафик приложения не уходит мимо выбранного интерфейса. Так же, если DNS интерфейса и DoH
  не ответили.
- `default` — соединения идут маршрутом по умолчанию, имена разрешает системный резолвер.

Новые соединения снова идут через интерфейс, как только он появится (адреса перечитываются
раз в 2 секунды). В `approute-run` то же задают `--on-unavailable` и `--ipv6`; запуск с GUID
отключённого сейчас интерфейса допустим — `approute-run` предупредит о действующей политике.

## approute-dns (проверка разрешения имён)

```powershell
approute-dns --adapter happ-xray ifconfig.me ya.ru github.com
```

Показывает, как имена разрешаются через выбранный интерфейс (тем же резолвером, что и hook-DLL):
через какой путь (NRPT, DNS интерфейса или DoH), за какое время и с каким TTL.

## approute-routes (прототип менеджера маршрутов)

```powershell
# адаптеры, маршруты по умолчанию и текущий выход в интернет
approute-routes list

# что будет изменено (ничего не меняет)
approute-routes plan --ensure-default "Подключение по локальной сети"

# применить и поддерживать; Ctrl+C — откатить и выйти (нужны права администратора)
approute-routes watch --ensure-default "Подключение по локальной сети"
```

| Параметр | Значение |
|---|---|
| `--primary IF` | основной интерфейс (по умолчанию — физический с лучшей метрикой); выбор VPN здесь — «глобальный переключатель» |
| `--ensure-default IF` | добавить на интерфейс `0/0` с низким приоритетом (можно несколько раз) |
| `--route PREFIX=IF` | закрепить подсеть за интерфейсом (можно несколько раз): трафик **всех** программ в неё идёт через этот интерфейс, остальной — как обычно. Удобно для сервиса, который доступен только через VPN, если программу нельзя запустить через `approute-run` (например, приложение из Microsoft Store) |
| `--metric N` | метрика вторичных интерфейсов, по умолчанию 5000 |

`IF` — ifIndex, GUID или имя интерфейса. Все изменения действуют только до перезагрузки.

Если VPN-клиент сам следит за своей метрикой или маршрутами и возвращает их, `watch` не
вступает с ним в бесконечную перезапись: после 5 исправлений одного объекта за минуту он
предупреждает о конфликте (с именем интерфейса) и 5 минут не трогает этот объект, затем
пробует снова. При выходе значения, которые клиент вернул себе, не перезаписываются.

## Совместимость приложений

Проверено на реальной системе (hook-DLL, x64). «Выбранный интерфейс» — тот, что задан правилом.

| Приложение | Внедрение | TCP | UDP | DNS |
|---|---|---|---|---|
| Telegram Desktop (в т.ч. из Microsoft Store) | ✅ | ✅ через выбранный интерфейс | ⚠️ звонки — см. ниже | ✅ через интерфейс (NRPT / DNS интерфейса / DoH) |
| Яндекс Браузер (Chromium) | ✅ browser process и `network.mojom.NetworkService` | ✅ через выбранный интерфейс | ✅ QUIC через выбранный интерфейс | ✅ через интерфейс (+ встроенный DoH браузера) |

Защиты Chromium от сторонних DLL (политика подписи модулей) внедрению не помешали: DLL работает
в основном процессе и в сетевой службе, в остальные дочерние процессы правило не внедряется.
Обновления приложений правило не ломают — оно задаётся при запуске, а не в файлах программы.

**Звонки Telegram (UDP).** При голосовом вызове Telegram открывает UDP-сокеты сразу на всех
интерфейсах и **явно** привязывает каждый к своему адресу (сбор ICE-кандидатов, как в WebRTC).
Hook-DLL перехватывает только привязку к «любому» адресу (wildcard) и заворачивает её на выбранный
интерфейс; явную привязку к конкретному интерфейсу она не меняет, иначе сломала бы сокет. Поэтому
медиапоток звонка может уйти не через выбранный интерфейс. Текстовые сообщения, загрузки и
подключение (TCP) идут через него. Надёжно привязать звонок к одному интерфейсу сможет только
WFP-драйвер ([#18](https://github.com/SkifSVD/AppRoute/issues/18)), работающий в ядре независимо от
способа создания сокета — это обосновывает его приоритет.

## Назначение и границы

AppRoute — инструмент для владельца компьютера и работает только на его системе с его согласия.
Он использует те же низкоуровневые механизмы Windows, что и некоторое вредоносное ПО (внедрение
DLL, перехват Winsock и DNS), поэтому в него заложены чёткие границы: действие только на
запущенные через AppRoute приложения и их потомков, только на процессы текущего пользователя,
отказ от вмешательства в защитное и системное ПО, прозрачность и обратимость. Подробнее —
в [SECURITY.md](SECURITY.md).

## Ограничения

- Если VPN-сервер не пропускает трафик в интернет (только корпоративная сеть), приложения,
  привязанные к этому туннелю, тоже смогут ходить только туда.
- VPN-клиенты с «kill switch» (WFP-фильтры, блокирующие трафик мимо туннеля) могут не дать
  вывести трафик на основной канал.
- Защита от утечек DNS в TUN-клиентах тоже работает через WFP. Например, Happ в режиме TUN
  запрещает порт 53 на всех интерфейсах, кроме своего, и в настройках это не отключается. Пока
  он включён, корпоративный DNS другого VPN (OpenVPN с NRPT) недоступен — и программам через
  AppRoute, и самой системе. AppRoute чужие фильтры не обходит.
- IPv6: обрабатываются `::/0`, `/1`, `2000::/3` и схема OpenVPN `2000::/4` + `3000::/4`.
  `fc00::/7` (ULA — внутренние сети, обычно самого VPN) намеренно не трогается.
- Приложения, которые сами привязывают сокеты к конкретным интерфейсам (голосовые звонки с
  ICE-кандидатами, например Telegram), hook-DLL привязать не может — нужен WFP-драйвер (#18).
  Подробнее — в разделе «Совместимость приложений».
