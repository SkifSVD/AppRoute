# AppRoute

Маршрутизация по приложениям для Windows: выберите программу и укажите, через какой сетевой
интерфейс (Wi-Fi, Ethernet, VPN-туннель) она ходит в сеть. Весь остальной трафик идёт через
основное подключение — независимо от того, в каком порядке подключались VPN-клиенты.

*Per-application network interface routing for Windows 10/11.*

> **Статус:** ранний прототип. Готовы консольный менеджер маршрутов, привязка TCP/UDP и DNS
> приложений через hook-DLL (x64 и x86), конфиг правил и окно правил `approute-gui`; остальной
> GUI — в работе ([план](https://github.com/SkifSVD/AppRoute/milestones)).

## Проблема

Каждый VPN-клиент (OpenVPN, Xray/Happ в TUN-режиме, WireGuard…) при подключении забирает
маршрут по умолчанию себе: ставит `0.0.0.0/0` с минимальной метрикой или пару
`0.0.0.0/1` + `128.0.0.0/1`. В итоге «главным» становится тот, кто подключился последним, а
приложения при переподключении уезжают в текущий туннель.

## Как AppRoute это решает

1. **Менеджер маршрутов** держит маршрут по умолчанию на основном интерфейсе:
   - поднимает метрику интерфейсов VPN (от неё зависит и порядок DNS-серверов);
   - заменяет расщеплённые `0/1` + `128/1` (в IPv6 — `2000::/3`, `2000::/4` + `3000::/4`) на `0/0`,
     который проигрывает основному;
   - добавляет `0/0` с низким приоритетом на интерфейсы без него, чтобы к ним можно было
     привязывать приложения;
   - следит за изменениями (переподключение VPN) и всё откатывает при выходе.
2. **Привязка приложений** *(в разработке)* — DLL внедряется в выбранный процесс и привязывает
   его сокеты (TCP и UDP) к IP выбранного интерфейса; DNS-запросы приложения идут через DNS этого
   интерфейса. Windows (strong host model) отправляет такие пакеты только маршрутами этого
   интерфейса.
3. **WFP-драйвер** `approute-wfp.sys` *(проверка)* — тот же результат на уровне ядра, без
   внедрения DLL и как бы программа ни была запущена: ярлык, автозапуск, другая программа.
   Подменяет локальный адрес соединений (TCP и UDP) и привязок UDP, в том числе явных — звонки
   с ICE-кандидатами. Ставится вместе со службой по отдельному флажку в окне согласия. Пока
   подписан только тестовой подписью и загружается лишь в тестовом режиме Windows (проверка — в
   виртуальной машине, см. «Драйвер: сборка и проверка»); для обычных систем нужна подпись
   Microsoft (attestation signing) — до неё правила действуют через hook-DLL. Что для подписи
   готово и что нужно владельцу сертификата — [docs/driver-signing.md](docs/driver-signing.md).

## Сборка

Нужны Visual Studio 2022+ с компонентом «Разработка классических приложений на C++» и CMake
(входит в VS). Зависимость [MinHook](https://github.com/TsudaKageyu/minhook) подключена
git-подмодулем.

```powershell
git clone --recurse-submodules https://github.com/SkifSVD/AppRoute.git
./build.ps1            # Release → build/bin/Release
./build.ps1 -Config Debug
./build.ps1 -Test      # сборка и модульные тесты (ctest)
```

### Версии и выпуски

Версия — `X.Y.Z`, считается при каждой сборке по тегам выпусков git (`cmake/GitVersion.cmake`):

- на теге `vX.Y.Z` — эта версия; после тега — следующий патч (`X.Y.Z+1`);
- строка `+semver: minor` в сообщении коммита после тега поднимает минор, `+semver: major` — мажор;
- пока тегов нет — базовая версия из `project(AppRoute VERSION ...)` в `CMakeLists.txt`; ею же
  можно вручную поднять номер.

Версия записана в свойствах каждого exe/dll (вкладка «Подробно»), её печатает `--version` у утилит,
показывает меню значка окна правил и первая строка журналов службы и hook-DLL. Полная строка
сборки — с коммитом, например `0.2.1+1a2b3c4d`, а `-dirty` в конце значит, что собрано
с незакоммиченными изменениями.

```powershell
./build.ps1 -Publish -Zip        # поставка deploy\AppRoute-<версия>\ и zip, тег v<версия> → origin
./build.ps1 -Publish -Installer  # и установщик deploy\AppRoute-<версия>-setup.exe
./build.ps1 -Publish -NoTag      # поставка без тега
./build.ps1 -Publish -NoTagPush  # тег только локально
./build.ps1 -Publish -Version 0.3.1   # ручная версия (хотфикс), тег не ставится
```

Тег ставится, только если публикация идёт из `main`, дерево было чистым при запуске, а коммит
уже есть в `origin/main`; иначе скрипт печатает команды для ручной постановки. Без нового тега
номер следующих сборок не растёт. Изменения по выпускам — в [CHANGELOG.md](CHANGELOG.md).

### Драйвер: сборка и проверка

Нужен WDK (Windows Driver Kit) той же версии, что и SDK.

```powershell
./tools/driver/Build-Driver.ps1      # build\driver\approute-wfp.sys с тестовой подписью
./tools/driver/Build-Driver.ps1 -Package   # и пакет для подписи Microsoft: build\driver\approute-wfp.cab
```

Драйвер с тестовой подписью Windows загружает только в тестовом режиме (`bcdedit /set
testsigning on`), а включать его на рабочей системе не стоит. Поэтому проверка — в виртуальной
машине Hyper-V (скрипты — от администратора, на компьютере с Hyper-V):

```powershell
./tools/vm/New-TestVm.ps1 -Iso путь\к\Win11.iso    # ВМ с двумя сетевыми картами
./tools/vm/New-TestVm.ps1 -AfterInstall            # после установки Windows: Secure Boot ВМ выключен
./tools/vm/Copy-TestKit.ps1                        # программы, драйвер и сценарий — в C:\AppRouteTest ВМ
```

В ВМ (после `bcdedit /set testsigning on` и перезагрузки), от администратора:
`powershell -ExecutionPolicy Bypass -File C:\AppRouteTest\Test-Driver.ps1` — драйвер и `wfp`,
с `-Service` — служба с драйвером. Сценарий направляет curl и тестовую UDP-программу во вторую
сетевую карту и проверяет, с какого адреса они вышли, а в конце — что всё снято.

## CI

Сборка выполняется на self-hosted runner с метками `self-hosted, Windows, X64, approute`
(нужны Visual Studio с C++ и PowerShell 7). Пока runner не запущен, задания ждут в очереди.
Сборки идут на каждый push в `main`, на pull request и на тег выпуска `v*`; артефакт называется
`approute-<версия>-x64`.

## Установка, обновление и откат

Установщик `AppRoute-<версия>-setup.exe` — один файл со всей программой внутри (выпуски — на
странице [Releases](https://github.com/SkifSVD/AppRoute/releases); обновления вручную: скачать
установщик новой версии и запустить).

- **Установка** — для текущего пользователя в `%LOCALAPPDATA%\Programs\AppRoute`, без прав
  администратора; ярлык «AppRoute» в меню «Пуск», запись в «Параметры → Приложения». Папку можно
  выбрать, но только пустую или с прежней установкой AppRoute.
- **Обновление** — тем же установщиком поверх: открытое окно правил закрывается и после обновления
  открывается снова; прежние файлы переносятся в `.backup\` папки установки (хранятся две последние
  версии). Правила и настройки (`%APPDATA%\AppRoute`) и пароли прокси не меняются. Программы,
  запущенные через AppRoute, закрывать не нужно: занятые ими файлы Windows разрешает перенести.
- **Откат** — «Параметры → Приложения → AppRoute → Изменить» (или установщик ещё раз) →
  «Откатить к …»: возвращается последняя сохранённая версия, а текущая сохраняется вместо неё,
  поэтому повторный откат возвращает обратно. Ставить более старую версию поверх тоже можно.
- **Удаление** — «Параметры → Приложения → AppRoute → Удалить»: программа, её копии, ярлыки
  AppRoute и запись автозапуска. Правила и настройки — только по флажку.
- **Служба AppRoute** (менеджер маршрутов) ставится, как и раньше, из окна правил в
  `%ProgramFiles%\AppRoute`. Если она установлена, установщик при обновлении и откате предлагает
  обновить её (запрос UAC), а при удалении удаляет её вместе с драйвером.

Без окон (например, из сценария):

```powershell
AppRoute-0.2.0-setup.exe --install [--dir ПАПКА] [--no-shortcuts] --silent
AppRoute-0.2.0-setup.exe --rollback --silent
AppRoute-0.2.0-setup.exe --uninstall [--remove-settings] --silent
```

Коды выхода: 0 — готово, 1 — ошибка, 2 — отменено или нечего делать; журнал —
`%TEMP%pproute-setup.log`. В тихом режиме служба обновляется или удаляется, только если
установщик запущен от администратора (иначе обновление — с замечанием в журнале, а удаление
не выполняется). Установщик пока не подписан: Windows SmartScreen покажет «неизвестный издатель».

## approute-gui (окно правил)

```powershell
approute-gui                      # правила из %APPDATA%\AppRoute\config.json
approute-gui --config FILE        # другой файл правил
approute-gui --run PROGRAM [-- ARGS]   # запустить программу по правилу без окна (так работают ярлыки)
```

**Весь трафик через** — глобальный переключатель основного интерфейса (вверху окна и в меню
значка в области уведомлений): «автоматически» (основное физическое подключение) или любой
подключённый интерфейс, например VPN. Правила программ работают независимо от него. Выбор
хранится в поле `primary` конфига; применяет его менеджер маршрутов — на лету, без перезапуска.
Пока менеджер не запущен, окно показывает, через какой интерфейс трафик идёт на самом деле.

**Менеджер маршрутов** запускается кнопкой рядом с переключателем (или из меню значка) только
после явного согласия: окно объясняет, что он делает, и показывает конкретный план изменений, затем
Windows запрашивает права администратора (UAC). Само окно работает без них. Менеджер
(`approute-routes serve`) работает без консоли, пишет журнал в
`%LOCALAPPDATA%\AppRoute\routes.log` и берёт политику из конфига: основной интерфейс,
маршрут 0/0 с низким приоритетом на интерфейсах правил, закреплённые подсети (`routes`).
Изменения конфига и подключение VPN он подхватывает сам. Остановка — той же кнопкой; все
изменения откатываются. Окно и менеджер связаны именованным каналом: менеджер принимает команды
только от `approute-gui.exe` из своей папки под вашим пользователем, окно — только от канала,
созданного процессом с правами администратора. Если выбранный VPN отключится, трафик пойдёт через автоматически выбранный
интерфейс, а не пропадёт. Закрытое окно остаётся в области уведомлений; выход — в меню значка.

**Служба.** В том же окне согласия можно выбрать «Запускать постоянно — службой Windows»: менеджер
маршрутов ставится службой «AppRoute» и работает и после перезагрузки, даже без открытого окна.
Файлы копируются в `%ProgramFiles%\AppRoute`, в меню «Пуск» появляется ярлык «AppRoute» на
установленное окно, журнал — `%ProgramData%\AppRoute\routes.log`. Запуск и остановка службы
после установки — той же кнопкой, без UAC; удаление — кнопкой остановки («Удалить службу») или в
меню значка, все изменения маршрутов откатываются. Без драйвера служба только держит маршруты
по конфигу, а правила программ действуют на программы, запущенные через AppRoute. На компьютере
работает один менеджер маршрутов — служба, запущенный из окна или `watch`.

**Драйвер.** Если рядом с окном лежит `approute-wfp.sys`, в окне согласия есть флажок «Вместе со
службой установить драйвер approute-wfp» (по умолчанию снят). С драйвером служба применяет правила
к любому запуску программ из списка — по полному пути, только к вашим процессам — и обновляет их
при правке правил и смене адресов интерфейсов. Правила с одним именем файла (без пути) и правила
через прокси драйвер не применяет — для них остаётся запуск через AppRoute. DNS драйвер не меняет:
программы, запущенные не через AppRoute, разрешают имена системой. Драйвер удаляется вместе со
службой. Если он не установился (например, Windows не приняла подпись), служба всё равно
ставится, а окно сообщает причину.

Список правил «программа → интерфейс» с текущим состоянием интерфейса (подключён, отключён,
нет в системе) — оно обновляется само каждые 3 секунды, например при подключении VPN.

- **Добавить** — мастер из трёх шагов:
  1. программа — из установленных в Windows (ярлыки меню «Пуск» и зарегистрированные программы,
     с поиском), а если её там нет — файл программы или ярлык (`.lnk`), который указывает на неё;
  2. интерфейс — из подключённых сейчас или из истории (ранее выбранные, например отключённый VPN),
     или SOCKS5-прокси (из других правил или новый — «Другой SOCKS5-прокси…», см. «Через
     SOCKS5-прокси вместо интерфейса»);
  3. что делать, если интерфейс недоступен: блокировать или пустить обычным маршрутом.

  DNS, IPv6 и дочерние процессы получают значения по умолчанию. Правило для той же программы
  дважды не создаётся. Приложения из Microsoft Store и пакетов MSIX тоже в списке (расположение
  «Microsoft Store / MSIX»): правило для них действует при запуске через AppRoute, а с драйвером
  WFP — при любом запуске; см. «Приложения из Microsoft Store и MSIX».
- **Изменить** — все настройки правила: программа (полный путь, ярлык, или только имя файла —
  тогда правило действует в любом каталоге), интерфейс или SOCKS5-прокси, недоступность
  интерфейса, DNS, IPv6, дочерние процессы, запуск при входе в Windows (см. ниже). У прокси в
  списке видно, отвечает ли он (для локального прокси).
- **Удалить** — с подтверждением (или клавиша Delete).
- **Запустить** — программа стартует с правилом, как через `approute-run`, в том числе приложение
  из пакета.
- **Ярлык…** — ярлык на рабочем столе или в меню «Пуск» (папка AppRoute) со значком программы:
  он запускает её через AppRoute (`approute-gui --run`), без окна и консоли. Если правило потом
  удалить, ярлык спросит, запустить ли программу без AppRoute. Для правила с одним именем файла
  ярлык не создаётся — нужен полный путь.
- **Обновить** — перечитать файл правил (его могли изменить `approute-config` или другой экземпляр).

### Запуск при входе в Windows

Программа из автозагрузки Windows стартует мимо AppRoute, и без драйвера её трафик не
направляется. Поэтому у правила есть флажок «Запускать при входе в Windows через AppRoute»
(`approute-config autostart PROGRAM on|off`, `add ... --autostart`):

- Если флажок включён хотя бы у одного правила, AppRoute добавляет **одну** запись автозагрузки
  для себя — «AppRoute» (`approute-gui.exe --autostart`) в автозагрузке текущего пользователя. Она
  видна в «Параметры → Приложения → Автозагрузка». Флажков нет — записи нет. В списке правил
  такие правила помечены «[при входе]».
- При входе AppRoute ждёт, пока интерфейс правила поднимется с адресом или прокси начнёт
  отвечать (VPN часто подключается позже входа), и запускает программу так же, как кнопка
  «Запустить», в том числе приложения из пакетов. Ожидание — не дольше 3 минут; после этого
  программа запускается всё равно, а правило соблюдает hook-DLL (по умолчанию блокирует
  соединения, пока интерфейса нет). Ошибки — одним окном сообщения.
- Чужие записи автозагрузки AppRoute не меняет. Если у программы есть своя включённая
  автозагрузка (реестр или папка «Автозагрузка»), окно и `approute-config` подскажут её
  отключить: иначе программа запустится ещё раз — мимо AppRoute.
- Нужен полный путь к программе (или приложение из пакета).

Правила хранятся в том же `config.json`, что у `approute-config` и `approute-run`. Если файл
не читается, окно сообщит об ошибке и отключит правку, чтобы не перезаписать ваши данные.
Окно работает с правами пользователя и поддерживает разные масштабы мониторов (Per-Monitor DPI).

### Журналы

| Журнал | Где |
|---|---|
| Программы, запущенные из окна, с ярлыка AppRoute и при входе в Windows (hook-DLL) | `%LOCALAPPDATA%\AppRoute\logs\<программа>.log` |
| Менеджер маршрутов, запущенный из окна | `%LOCALAPPDATA%\AppRoute\routes.log` |
| Служба AppRoute | `%ProgramData%\AppRoute\routes.log`, установка — `install.log` там же |
| Установщик | `%TEMP%\approute-setup.log` |

Папку журналов программ открывает пункт «Журналы запусков» в меню значка. Журнал больше 1 МБ при
следующем запуске переносится в `.1`. В журнале hook-DLL видно, через какой интерфейс или прокси
программа разрешала имена и соединялась, и что было заблокировано. Перед тем как выкладывать
журнал в задачу, уберите из него адреса и имена хостов.

## approute-run (запуск программы через интерфейс)

```powershell
approute-run --adapter happ-xray -- "C:\Program Files\App\app.exe" --some-arg
approute-run --adapter "Беспроводная сеть" --log C:\temp\approute.log -- curl.exe https://ifconfig.me/ip
approute-run -- "C:\Program Files\App\app.exe"     # интерфейс — из правила в конфиге
```

Без `--adapter` правило для программы берётся из конфига (см. `approute-config` ниже);
`--config FILE` — другой файл конфига.

Программа запускается с `approute-hook64.dll`, которая перед каждым соединением привязывает
сокет к IP выбранного интерфейса (`connect`, `WSAConnect`, `ConnectEx`, `sendto`, `WSASendTo`,
`WSASendMsg`, `bind` на «любой адрес»). Локальная сеть, loopback и подсети других интерфейсов
не перенаправляются. Если у интерфейса нет адреса нужного семейства, соединение блокируется
или идёт маршрутом по умолчанию — по политике правила (см. «Если интерфейс правила недоступен»).
Права администратора не нужны, но у интерфейса должен быть маршрут `0/0` (см. `--ensure-default`
ниже). Поддерживаются 64- и 32-битные программы: для процесса другой разрядности (32-битная
программа, или 64-битный ребёнок 32-битного родителя) DLL внедряет помощник
`approute-inject32.exe` / `approute-inject64.exe`, поэтому все файлы из `bin` должны лежать вместе.

Правило распространяется на дочерние процессы (браузеры работают с сетью в отдельном процессе):
DLL перехватывает `CreateProcessInternalW`, запускает ребёнка приостановленным, внедряется в него
и восстанавливает правило в окружении, если родитель передал своё. `--no-children` — отключить.

DNS приложения тоже идёт через выбранный интерфейс: DLL перехватывает `getaddrinfo`,
`GetAddrInfoW` и `GetAddrInfoExW` и разрешает имена через DNS-серверы интерфейса, а если они
недоступны (VPN-клиент часто блокирует порт 53 в обход туннеля) — через DNS-over-HTTPS по тому
же интерфейсу. Так DNS не утекает в системный резолвер, который ходит через основной канал.
Подходят серверы в подсети интерфейса или с лучшим маршрутом через него. Имена из таблицы NRPT
(так корпоративные VPN, например OpenVPN, задают DNS внутренних доменов) разрешаются только у
серверов правила NRPT, если они достижимы через интерфейс, — внутренние имена не уходят во
внешний DoH.
`APPROUTE_DNS=system` отключает перехват. Требуется Windows 11 (используется `DnsQueryEx` с
пользовательскими серверами).

### Через SOCKS5-прокси вместо интерфейса

```powershell
approute-run --proxy 127.0.0.1:10808 -- curl.exe https://example.com
```

Цель правила может быть не интерфейсом, а SOCKS5-прокси — например, локальным прокси клиента
Xray/V2Ray, который работает без TUN (в режиме «системный прокси»). Тогда:

- **TCP** программы идёт через прокси: DLL соединяется с прокси и проходит рукопожатие SOCKS5
  внутри `connect`/`WSAConnect`/`ConnectEx` (в том числе на неблокирующих сокетах), `getpeername`
  возвращает адрес, с которым соединялась программа;
- **имена разрешает прокси**: `getaddrinfo`/`GetAddrInfoW`/`GetAddrInfoExW` (в том числе
  асинхронный, как у .NET) отдают программе служебный адрес из `198.18.0.0/15`, а прокси получает
  имя (`CONNECT` или заголовок UDP по имени). `localhost` и имена без точки (узлы локальной сети)
  разрешает система;
- **UDP** идёт через прокси командой UDP ASSOCIATE: на каждое назначение — управляющее соединение
  с прокси на всё время жизни сокета и внутренний сокет на loopback, через который DLL добавляет и
  снимает заголовок SOCKS5. Программа получает чистые данные при любом способе приёма
  (синхронном, `OVERLAPPED`, порт завершения), а адрес отправителя — исходный. Если прокси UDP не
  поддерживает, датаграммы блокируются, а не уходят мимо него (QUIC в браузерах тогда
  переключается на TCP);
- **локальная сеть**, loopback и подсети интерфейсов — напрямую;
- прокси не отвечает — соединения программы не устанавливаются; мимо прокси трафик не идёт.

Адрес прокси — IP-адрес и порт; фрагменты UDP (поле FRAG) не поддерживаются.

**Логин и пароль** (RFC 1929) — если прокси требует вход. Они хранятся не в конфиге, а в диспетчере
учётных данных Windows текущего пользователя (запись `AppRoute/SOCKS5/адрес:порт`), и действуют
для всех правил с этим прокси. hook-DLL читает их сама в процессе программы — пароль не
передаётся через командную строку или окружение и не пишется в журнал.

```powershell
approute-config proxy-auth 127.0.0.1:10808 user      # пароль спрашивается без отображения
approute-config proxy-auth 127.0.0.1:10808 --remove
```

В окне логин и пароль задаются в диалоге прокси («Другой SOCKS5-прокси…»); состояние прокси в
списке показывает, принят ли вход. Так можно, например,
пустить выбранные программы через Happ в режиме «системный прокси» вместе с корпоративным VPN:
без TUN Happ не ставит свою защиту DNS, и корпоративный DNS продолжает работать.

## approute-config (правила)

Правила хранятся в `%APPDATA%\AppRoute\config.json`:

```json
{
  "version": 1,
  "primary": "auto",
  "rules": [
    { "app": "C:\\Program Files\\App\\app.exe",
      "target": { "type": "adapter", "id": "{GUID интерфейса}" },
      "onUnavailable": "block", "dns": "adapter", "ipv6": "follow", "includeChildren": true },
    { "app": "curl.exe", "target": { "type": "proxy", "socks5": "127.0.0.1:10808" } }
  ]
}
```

```powershell
approute-config add "C:\Program Files\App\app.exe" --adapter happ-xray
approute-config add telegram.exe --adapter happ-xray --no-children   # по имени файла, в любом каталоге
approute-config add curl.exe --proxy 127.0.0.1:10808                 # через SOCKS5-прокси
approute-config packages                                             # приложения из Store и MSIX
approute-config add "Claude_pzs8sxrjxfjjc!Claude" --adapter happ-xray  # приложение из пакета
approute-config autostart "C:\Program Files\App\app.exe" on        # запускать при входе в Windows
approute-config show
approute-config remove telegram.exe
approute-config check
```

| Поле | Значения |
|---|---|
| `app` | полный путь (можно с `%ПЕРЕМЕННЫМИ%`), только имя файла (полный путь важнее имени) или приложение из пакета `Семейство!Id` |
| `target.id` | GUID интерфейса — не меняется при переименовании; `add` переводит имя/ifIndex в GUID |
| `target.socks5` | для `type: proxy` — адрес SOCKS5-прокси, например `127.0.0.1:10808`; `onUnavailable` и `ipv6` к нему не применяются |
| `onUnavailable` | `block` (по умолчанию) / `default` — если интерфейс отключён, см. ниже |
| `dns` | `adapter` (по умолчанию) / `system` |
| `ipv6` | `follow` (как `onUnavailable`) / `block` / `default` — если у интерфейса нет IPv6 |
| `includeChildren` | `true` (по умолчанию) / `false` |
| `autostart` | `true` — запускать при входе в Windows через AppRoute; по умолчанию поля нет (`false`) |

`routes` — подсети, закреплённые за интерфейсом (`[{ "prefix": "160.79.104.0/23", "adapter":
"{GUID}" }]`): трафик **всех** программ в них идёт через этот интерфейс, остальной — как обычно.
Применяет менеджер маршрутов, запущенный из окна; в `approute-routes watch` то же задаёт `--route`.

`knownAdapters` — история выбранных интерфейсов (GUID, имя, описание): по ней окно и
`approute-config show` показывают имя интерфейса, которого сейчас нет в системе (VPN отключён),
и предлагают его при добавлении правила. Заполняется само.

Неизвестные поля игнорируются; конфиг более новой версии не загружается, а не портится.

### Приложения из Microsoft Store и MSIX

Программы, установленные пакетом (например, Claude для Windows), лежат в
`C:\Program Files\WindowsApps`, и путь к ним меняется с каждым обновлением. Поэтому правило для
такого приложения хранит его идентификатор (AUMID) — `Семейство!Id`, например
`Claude_pzs8sxrjxfjjc!Claude`; список — в мастере окна или `approute-config packages`. Подходят
приложения полного доверия (обычные программы Win32 в пакете), только текущего пользователя.

Правило действует двумя способами:

- **При запуске через AppRoute** (#59) — кнопка «Запустить», ярлык AppRoute или
  `approute-run -- "Семейство!Id" [аргументы]`. Подпись и драйвер не нужны, доступны и интерфейс,
  и прокси. Процесс приложения из пакета создаёт сама Windows, поэтому AppRoute пользуется её
  документированным механизмом отладки пакетов (`IPackageDebugSettings`, тот же, что у Visual
  Studio): на время запуска для пакета регистрируется помощник `approute-inject`, Windows создаёт
  процесс приостановленным, помощник подключает hook-DLL и продолжает его. Сразу после запуска
  настройка снимается; если AppRoute прервали, она снимается при следующем запуске окна или
  `approute-run`. Если приложение уже открыто без AppRoute, окно предупредит: новое окно может
  открыться в старом процессе, мимо правила. Приложение, запущенное из меню «Пуск» или другой
  программой, без драйвера не направляется.
- **Драйвером WFP** — при любом запуске. Служба находит путь к exe по пакету, установленному у
  пользователя, при каждом применении правил и перепроверяет его раз в 30 секунд: после обновления
  пакета фильтр переходит на новую версию. Прокси драйвер не применяет.
- С `includeChildren` (по умолчанию) правило действует и на дочерние процессы, а у драйвера — на
  другие программы полного доверия того же пакета (у Claude — помощники SSH).
- Ограничение: если тот же пакет в это время отлаживается в Visual Studio, запуск через AppRoute
  сбросит настройку её отладчика для пакета.

Так подсеть больше не нужно закреплять за интерфейсом (`routes`) ради одного приложения из пакета:
обычное правило действует только на него.

**Если интерфейс правила недоступен** (VPN отключён, у интерфейса нет адреса нужного семейства):

- `block` — соединения завершаются ошибкой `WSAENETUNREACH`, DNS-запросы — `WSATRY_AGAIN`;
  трафик приложения не уходит мимо выбранного интерфейса. Так же, если DNS интерфейса и DoH
  не ответили.
- `default` — соединения идут маршрутом по умолчанию, имена разрешает системный резолвер.

Новые соединения снова идут через интерфейс, как только он появится (адреса перечитываются
раз в 2 секунды). В `approute-run` то же задают `--on-unavailable` и `--ipv6`; запуск с GUID
отключённого сейчас интерфейса допустим — `approute-run` предупредит о действующей политике.

## approute-dns (проверка разрешения имён)

```powershell
approute-dns --adapter happ-xray ifconfig.me ya.ru github.com
```

Показывает, как имена разрешаются через выбранный интерфейс (тем же резолвером, что и hook-DLL):
через какой путь (NRPT, DNS интерфейса или DoH), за какое время и с каким TTL.

## approute-routes (прототип менеджера маршрутов)

```powershell
# адаптеры, маршруты по умолчанию и текущий выход в интернет
approute-routes list

# что будет изменено (ничего не меняет)
approute-routes plan --ensure-default "Подключение по локальной сети"

# применить и поддерживать; Ctrl+C — откатить и выйти (нужны права администратора)
approute-routes watch --ensure-default "Подключение по локальной сети"

# установить менеджер службой Windows (политика из конфига) и удалить её — от администратора;
# --with-driver — и драйвер approute-wfp.sys из папки approute-routes (удаляется вместе со службой)
approute-routes install-service --config "%APPDATA%\AppRoute\config.json" [--with-driver]
approute-routes uninstall-service

# проверка драйвера без службы: загрузить, применять правила конфига (Ctrl+C — снять), выгрузить
approute-routes install-driver --sys build\driver\approute-wfp.sys
approute-routes wfp --config "%APPDATA%\AppRoute\config.json"
approute-routes uninstall-driver
```

| Параметр | Значение |
|---|---|
| `--primary IF` | основной интерфейс; без параметра — из поля `primary` конфига (переключатель в `approute-gui`, применяется на лету), `auto` — физический с лучшей метрикой |
| `--config FILE` | файл правил для `primary` (по умолчанию `%APPDATA%\AppRoute\config.json`) |
| `--ensure-default IF` | добавить на интерфейс `0/0` с низким приоритетом (можно несколько раз) |
| `--route PREFIX=IF` | закрепить подсеть за интерфейсом (можно несколько раз): трафик **всех** программ в неё идёт через этот интерфейс, остальной — как обычно. Удобно для сервиса, который доступен только через VPN, если программу нельзя запустить через `approute-run`, а драйвера WFP нет |
| `--metric N` | метрика вторичных интерфейсов, по умолчанию 5000 |

`IF` — ifIndex, GUID или имя интерфейса. Все изменения действуют только до перезагрузки.

Если VPN-клиент сам следит за своей метрикой или маршрутами и возвращает их, `watch` не
вступает с ним в бесконечную перезапись: после 5 исправлений одного объекта за минуту он
предупреждает о конфликте (с именем интерфейса) и 5 минут не трогает этот объект, затем
пробует снова. При выходе значения, которые клиент вернул себе, не перезаписываются.

## Совместимость приложений

Проверено на реальной системе (hook-DLL, x64). «Выбранный интерфейс» — тот, что задан правилом.

| Приложение | Внедрение | TCP | UDP | DNS |
|---|---|---|---|---|
| Telegram Desktop (в т.ч. из Microsoft Store) | ✅ | ✅ через выбранный интерфейс | ⚠️ звонки — см. ниже | ✅ через интерфейс (NRPT / DNS интерфейса / DoH) |
| Яндекс Браузер (Chromium) | ✅ browser process и `network.mojom.NetworkService` | ✅ через выбранный интерфейс | ✅ QUIC через выбранный интерфейс | ✅ через интерфейс (+ встроенный DoH браузера) |

Защиты Chromium от сторонних DLL (политика подписи модулей) внедрению не помешали: DLL работает
в основном процессе и в сетевой службе, в остальные дочерние процессы правило не внедряется.
Обновления приложений правило не ломают — оно задаётся при запуске, а не в файлах программы.

Основной процесс браузера при запуске открывает двухстековые UDP-сокеты mDNS (порт 5353, поиск
устройств в локальной сети) и запрашивает их адрес до первой отправки. Такие сокеты привязываются
к `::`, как просила программа, и ходят только в локальную сеть (`ff02::fb`). Если с такого сокета
программа пойдёт за пределы локальной сети, действует политика правила: «блокировать» — отправка
блокируется, «маршрутом по умолчанию» — идёт как есть (с записью в журнале).

**Звонки Telegram (UDP).** При голосовом вызове Telegram открывает UDP-сокеты сразу на всех
интерфейсах и **явно** привязывает каждый к своему адресу (сбор ICE-кандидатов, как в WebRTC).
Hook-DLL перехватывает только привязку к «любому» адресу (wildcard) и заворачивает её на выбранный
интерфейс; явную привязку к конкретному интерфейсу она не меняет, иначе сломала бы сокет. Поэтому
медиапоток звонка может уйти не через выбранный интерфейс. Текстовые сообщения, загрузки и
подключение (TCP) идут через него. Надёжно привязать звонок к одному интерфейсу может
WFP-драйвер ([#18](https://github.com/SkifSVD/AppRoute/issues/18)): он работает в ядре независимо от
способа создания сокета и подменяет и явную привязку UDP. Звонки Telegram с драйвером ещё не
проверялись — драйвер проверен в ВМ на curl и тестовой UDP-программе.

**Happ (TUN) вместе с корпоративным VPN (OpenVPN).** Программы, которые нельзя запустить через
AppRoute, или сервис, доступный только через корпоративный VPN, можно вывести из туннеля Happ его
же настройками (*Настройки → Дополнительные настройки*):

- **Исключённые маршруты** — подсеть корпоративного сервиса: туннель не забирает трафик к ней, и
  он идёт маршрутом корпоративного VPN;
- **Исключения для системного прокси** — тот же адрес или подсеть, если включён «Системный
  прокси»: программы, которые ходят через системный прокси (браузеры, многие программы на WinINet
  и .NET), соединяются с сервисом напрямую, а не через прокси Happ.

Проверить, через какой интерфейс пойдёт трафик к сервису:
`Find-NetRoute -RemoteIPAddress АДРЕС | Select-Object -First 1 InterfaceAlias` — должен быть
адаптер корпоративного VPN. Адрес из подсети самого адаптера VPN для проверки не годится: до него
трафик и так идёт напрямую. Ограничение по DNS остаётся (см. «Ограничения»): так работают сервисы,
к которым программа подключается по IP-адресу или чьи имена разрешаются без корпоративного DNS.

## Назначение и границы

AppRoute — инструмент для владельца компьютера и работает только на его системе с его согласия.
Он использует те же низкоуровневые механизмы Windows, что и некоторое вредоносное ПО (внедрение
DLL, перехват Winsock и DNS, драйвер ядра), поэтому в него заложены чёткие границы: действие
только на выбранные пользователем приложения (без драйвера — только запущенные через AppRoute и
их потомков), только на процессы пользователя, давшего согласие,
отказ от вмешательства в защитное и системное ПО, прозрачность и обратимость. Подробнее —
в [SECURITY.md](SECURITY.md).

## Ограничения

- Если VPN-сервер не пропускает трафик в интернет (только корпоративная сеть), приложения,
  привязанные к этому туннелю, тоже смогут ходить только туда.
- VPN-клиенты с «kill switch» (WFP-фильтры, блокирующие трафик мимо туннеля) могут не дать
  вывести трафик на основной канал.
- Защита от утечек DNS в TUN-клиентах тоже работает через WFP. Например, Happ в режиме TUN
  запрещает порт 53 на всех интерфейсах, кроме своего, и в настройках это не отключается. Пока
  он включён, корпоративный DNS другого VPN (OpenVPN с NRPT) недоступен — и программам через
  AppRoute, и самой системе. AppRoute чужие фильтры не обходит. Сам трафик к корпоративному
  сервису можно вывести из туннеля настройками Happ — см. «Совместимость приложений».
- IPv6: обрабатываются `::/0`, `/1`, `2000::/3` и схема OpenVPN `2000::/4` + `3000::/4`.
  `fc00::/7` (ULA — внутренние сети, обычно самого VPN) намеренно не трогается.
- Приложения, которые сами привязывают сокеты к конкретным интерфейсам (голосовые звонки с
  ICE-кандидатами, например Telegram), hook-DLL привязать не может — нужен WFP-драйвер (#18).
  Подробнее — в разделе «Совместимость приложений».
- WFP-драйвер пока подписан только тестовой подписью: на обычной системе Windows его не загрузит
  (окно об этом сообщит), нужна подпись Microsoft. Драйвер не меняет DNS и не применяет правила с
  одним именем файла и правила через прокси. Без драйвера правила для приложений из Microsoft Store
  и MSIX действуют только при запуске через AppRoute.
- Без драйвера правило действует только на копию программы, запущенную через AppRoute. Если
  программа уже открыта обычным способом, многие программы (браузеры, мессенджеры) передают
  новое окно уже работающей копии — и трафик идёт мимо правила. AppRoute к работающим процессам не
  подключается, а предупреждает об этом при запуске: закройте программу полностью (в том числе из
  трея и фонового режима) и запустите через AppRoute снова.
